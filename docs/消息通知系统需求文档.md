## 1. 文档目的

本文档基于现有 `drawstarts-notify-serve` 仓库能力，明确：

1. **现有功能基线**（必须保留并对接方可兼容演进）
2. **独立三方仓库**的定位与接入契约
3. **代码重构**范围与质量目标
4. **性能与安全**优化要求
5. **消息通知基础能力**的拓展规划

目标是将本系统从「可嵌入宿主的早期 WebSocket 频道库」演进为「可独立发布、可被多业务系统复用的通用实时消息通知中间件」。

---

## 2. 背景与现状

### 2.1 产品定位（现状）

当前包是 **WebSocket 频道 Pub/Sub 通知库**，不是 HTTP 邮件/短信网关。宿主应用（Nest / Express 等）通过 `init` 注入鉴权与持久化钩子，客户端通过 WebSocket JSON 协议完成登录、进退频道与消息推送。

### 2.2 技术栈（现状）

| 层级 | 选型 |
|------|------|
| 语言 | TypeScript |
| 运行时 | Node.js |
| 传输 | WebSocket（`ws`） |
| 构建 | Vite Library Mode → UMD |
| 存储 | 进程内 `Map`（无 DB / 无消息队列） |
| HTTP / REST | 无 |
| 邮件 / 短信 / 移动推送 | 无 |

### 2.3 集成方式（现状）

```text
[宿主业务系统]
  ├─ verifyToken(token) → userInfo
  ├─ addLog(...)
  └─ addNotify(...)
        │
        ▼
  notifyServer.init({ config, verifyToken, addLog, addNotify })
        │
        ▼
  WebSocket.Server :port（默认 8030）
        │
        ▼
[WS 客户端] login → joinChannel → 收发 notify
```

### 2.4 已知问题（重构驱动）

| 类别 | 问题 |
|------|------|
| 功能残缺 | `getChannelAttribute` 已实现但未接入路由；`getAttributes` 恒返回空；`MSG_TYPE` / `sys` / 国际化未落地 |
| 安全缺口 | `type=notify` 无登录校验；默认 `verifyToken` 空实现；无 WSS / 限流 / Origin 白名单 / 消息 schema 校验 |
| 契约不一致 | `addNotify` 类型签名与实际调用参数不一致 |
| 缺陷 | 断开连接清理存在变量遮蔽，易产生僵尸连接；`generateId` 依赖 `window.crypto`，Node 不可用 |
| 可扩展性 | 纯内存状态，无法多实例水平扩展、无消息持久化、无离线补偿 |
| 工程化 | 依赖/构建配置不严谨；文档与协议说明不足；测试仅冒烟 |

## 3. 建设目标

### 3.1 总体目标

将本仓库建设为 **独立可发布的三方消息通知中间件**，满足：

- **可嵌入**：以 npm 包形式嵌入任意 Node 业务系统
- **可独立部署**：支持作为独立进程 / 容器运行（可选 HTTP 管理面）
- **能力完整**：覆盖实时通知系统的基础能力（鉴权、频道、定向、回执、离线、可观测）
- **安全可信**：默认安全，宿主可扩展策略
- **高性能**：高并发连接、低延迟推送、可水平扩展

### 3.2 非目标（本期不做）

- 不替代完整 IM（群聊、已读回执链路、富媒体会话等）
- 不内置具体邮件运营商 / 短信通道账号配置的运营后台（仅预留 Provider 接口）
- 不强制绑定特定业务库表结构（持久化由宿主或插件实现）

## 4. 角色与使用场景

| 角色 | 诉求 |
|------|------|
| 业务宿主系统 | 注入鉴权与落库逻辑，获得实时推送能力 |
| 前端 / 客户端 | 登录、订阅频道、接收通知、发送业务通知 |
| 运营 / 管理方 | 查看连接数、频道、推送成功率（可选管理 API） |
| 平台研发 | 维护独立仓库、版本发布、协议兼容 |

**典型场景**

1. 业务系统内实时状态同步（如房间、文档协作、任务进度）
2. 跨模块事件广播（订单状态、审核结果）
3. 多端在线用户定向提醒
4. 作为统一通知总线，后续扩展邮件/短信等离线通道

## 5. 现有功能需求（基线，必须保留）

以下能力为 **v1 兼容基线**，重构后必须继续支持（允许协议增强，但需提供兼容层或迁移说明）。

### 5.1 宿主初始化 API

```ts
notifyServer.init({
  config: { port: number },
  verifyToken: (token: string) => userInfo | Promise<userInfo>,
  addLog: (type, hostname, originalUrl, content) => void | Promise<void>,
  addNotify: (sendId, receiveId, notifyType, notifyMsg) => void | Promise<void>,
})
```

**要求**

- 统一并修正 `addNotify` 参数语义文档（发送方 / 接收方或频道 / 类型 / 内容）
- 钩子支持同步与异步（Promise）
- `port` 可配置，默认值明确（现状默认 8030）

### 5.2 客户端 WebSocket 协议（现状）

#### 5.2.1 消息大类（`SEND_TYPE`）

| type | 含义 |
|------|------|
| `request` | 请求类操作（需登录态校验，`login` 除外） |
| `notify` | 通知推送 |

#### 5.2.2 请求方法（`METHOD_TYPE`）

| 方法 | 现状 | 基线要求 |
|------|------|----------|
| `login` | 已实现 | 必须保留：token 校验、写入 clientMap、返回 feedback |
| `logout` | 已实现 | 必须保留：清理客户端与频道关系 |
| `joinChannel` | 已实现 | 必须保留：创建/加入频道并登记成员 |
| `leaveChannel` | 已实现 | 必须保留：退出频道 |
| `getAttributes` | 空实现 | 重构后补齐真实属性查询（见拓展） |
| `getChannelAttribute` | 死代码 | 重构后正式接入路由 |

#### 5.2.3 服务端下行类型（`WS_MSG_TYPE`）

| type | 含义 | 现状 |
|------|------|------|
| `feedback` | 请求回执 | 已用 |
| `notify` | 业务通知 | 已用 |
| `sys` | 系统消息 | 未用，需落地 |

#### 5.2.4 Feedback 结构

```ts
{
  type: "feedback",
  requestId: string,
  res: { status: boolean, method: string, data: any }
}
```

#### 5.2.5 Notify 广播结构

```ts
{
  type: "notify",
  notifyType: string,
  notifyMsg: string, // 或结构化对象（拓展后）
  channelName: string,
  userId: string,
  clientId: string
}
```

### 5.3 会话与频道模型（现状语义）

- **客户端会话**：`clientId`、`userId`、`userInfo`、`connectInfo`、`channelMap`、`loginTime`、`expireTime`
- **频道**：`channelName`、成员 `clientMap`、最近通知缓存 `notifyParamMap`
- **Token 有效期**：宿主返回 `expireTime`，否则默认 24h（`DAY_DURATION`）
- **连接元数据**：记录 `host` / `origin` / `userAgent` 并回调 `addLog`

### 5.4 发布形态（现状）

- npm 包名：`drawstarts-notify-serve`
- 构建产物：UMD（需演进为更适合 Node 的 ESM/CJS 双构建，见重构章节）

## 6. 独立三方仓库需求

### 6.1 仓库定位

本仓库作为 **通用实时消息通知中间件**，满足：

1. **独立版本管理与发布**（semver）
2. **零业务耦合**：不依赖具体业务库表、框架
3. **清晰接入契约**：Host Hooks + Client Protocol +（可选）Admin HTTP
4. **完整文档**：README、协议手册、接入示例、变更日志
5. **可测试**：单元测试 + 协议集成测试 + 示例工程

### 6.2 对外交付物

| 交付物 | 说明 |
|--------|------|
| npm 包 | 主入口 + 类型声明（`.d.ts`） |
| 协议文档 | WebSocket JSON 协议与错误码 |
| 宿主接入指南 | init 钩子、鉴权、落库建议 |
| 客户端 SDK（可选分期） | JS/TS 轻量封装 login/join/notify |
| Docker 镜像（可选） | 独立部署模式 |
| 示例 | Express / Nest 最小接入样例 |

### 6.3 两种运行模式

| 模式 | 说明 | 优先级 |
|------|------|--------|
| **嵌入模式（Library）** | 宿主 `init` 后同进程启动 WS | P0（兼容现状） |
| **独立服务模式（Standalone）** | 独立进程提供 WS + 可选 HTTP 管理面，通过配置/插件对接鉴权 | P1 |

### 6.4 插件化扩展点（必须设计）

宿主或独立部署时，通过接口注入：

| 扩展点 | 职责 |
|--------|------|
| `AuthProvider` | token 校验、续期、踢下线策略 |
| `NotifyStore` | 通知持久化 / 离线消息 |
| `Logger` | 结构化日志 |
| `Metrics` | 连接数、推送 QPS、失败率 |
| `ChannelPolicy` | 频道创建权限、成员上限、禁言等 |
| `TransportProvider`（拓展） | Email / SMS / Webhook / Push |

## 7. 重构需求

### 7.1 架构分层

建议重构为清晰分层（逻辑模块，不强制目录名一致）：

```text
├── protocol/          # 协议定义、校验、错误码
├── core/              # 连接管理、会话、频道、路由
├── auth/              # 鉴权与过期控制
├── delivery/          # 推送策略（频道/单播/广播）
├── adapters/          # Host hooks、Standalone 适配
├── observability/     # 日志、指标、健康检查
└── index.ts           # 对外 API
```

### 7.2 代码质量目标

| 项 | 要求 |
|----|------|
| 类型安全 | 补齐并修正 Interface；杜绝 `any` 滥用；导出公共类型 |
| 契约一致 | Host hooks、协议字段、实现三者一致 |
| 缺陷修复 | 修复断开清理遮蔽 bug；Node 可用的 ID 生成；接入死代码方法 |
| 依赖治理 | 移除未使用 lodash；修正构建 external；提升 Node 引擎下限到 LTS |
| 构建产物 | 提供 `ESM + CJS + d.ts`；UMD 可选保留或废弃并说明 |
| 测试 | 核心路由 / 鉴权 / 进退频道 / 推送 / 断线清理覆盖 |
| 可维护性 | 单一职责；禁止 300+ 行上帝类长期存在 |

### 7.3 API 兼容策略

- **主版本内**：保留现有 `init` 与核心 method 名称
- **破坏性变更**：升 major，并提供迁移指南
- 新增能力优先走可选字段 / 新 method，避免破坏旧客户端

## 8. 安全需求

### 8.1 鉴权与授权（P0）

| 需求 | 说明 |
|------|------|
| 全链路鉴权 | 除白名单方法（如 `login`、心跳）外，`request` 与 `notify` 均需有效会话 |
| Token 校验失败反馈 | 禁止静默 return；必须返回明确 `feedback` / 错误码 |
| 会话过期 | 过期自动 logout，并下发 `sys` 通知 |
| 频道权限 | 可配置：仅登录用户可加入；可选频道密码 / 白名单 / 角色校验（ChannelPolicy） |
| 发送权限 | 可配置：谁可向某频道发 notify（全员 / 指定角色 / 仅服务端） |

### 8.2 传输与入口安全（P0/P1）

| 需求 | 优先级 |
|------|--------|
| 支持 WSS（TLS）配置 | P0 |
| Origin / Host 白名单 | P0 |
| 消息体大小限制 | P0 |
| JSON Schema / 字段校验 | P0 |
| 连接与消息限流（IP / user / channel） | P0 |
| 防重放（可选 requestId + 时间窗） | P1 |
| 敏感字段脱敏日志 | P1 |

### 8.3 默认安全原则

- **默认拒绝**：未配置鉴权时，独立模式下拒绝启动或仅允许本地调试模式
- **最小权限**：客户端不可默认拥有全局广播能力
- **可审计**：关键连接、登录失败、越权发送均记录

## 9. 性能需求

### 9.1 指标目标（单机基线，可随硬件调整）

| 指标 | 目标（建议） |
|------|----------------|
| 并发连接 | ≥ 1w（可配置调优） |
| 频道推送延迟（同机房） | P95 < 50ms |
| 单连接消息吞吐 | 可配置上限，默认防刷 |
| 内存 | 连接元数据精简；避免无界 Map 增长 |
| 优雅下线 | 支持 drain + 超时断开 |

### 9.2 性能优化项

| 项 | 说明 |
|----|------|
| 推送索引 | 按频道成员索引推送，避免全表扫描 `clientMap` |
| 批量推送 | 同 Tick 合并写 / 背压控制 |
| 心跳与清理 | 心跳检测僵尸连接；定时清理过期会话与空频道 |
| 序列化 | 减少多余字段；大 payload 可选压缩（P2） |
| 多实例 | 引入 Redis / NATS / Redis PubSub 等做跨节点扇出（P1） |
| 可配置 | `maxConnections`、`maxChannelsPerClient`、`maxMembersPerChannel` |

### 9.3 可靠性

- 推送失败可重试（同连接）与失败回调
- 关键关键写失败时清理会话
- 进程退出时尽量通知客户端 `sys: server_shutdown`

## 10. 拓展能力需求（消息通知系统基础能力）

在现有「频道广播」之上，补齐通用通知系统能力。按优先级分期。

### 10.1 P0 — 协议与会话完善

| 能力 | 描述 | 验收标准 |
|------|------|----------|
| 心跳 `ping/pong` 或 `heartbeat` | 保活与僵尸清理 | 超时未心跳自动断开并清理 |
| 系统消息 `sys` | 踢下线、过期、维护公告 | 客户端可区分处理 |
| 错误码体系 | 统一 `code/message` | 文档列出全部错误码 |
| `getChannelAttribute` | 返回频道属性与最近通知缓存 | 方法可达且权限正确 |
| `getAttributes` | 返回客户端自身会话属性 | 非空、字段稳定 |
| 消息类型 `MSG_TYPE` | `all` / `channel` / `single` | 单播与频道播真实生效 |
| 服务端主动推送 API | 宿主调用 `server.notify(...)` 无需伪造客户端包 | 示例可跑通 |

### 10.2 P1 — 投递与可靠性

| 能力 | 描述 |
|------|------|
| 离线消息 | 用户不在线时入库，登录后拉取/推送 |
| 消息持久化钩子 | `NotifyStore.save/list/ack` |
| ACK 确认 | 客户端确认已收，支持至少一次投递语义 |
| 消息 ID | 全局唯一 `messageId`，便于去重与追踪 |
| 历史拉取 | `pullHistory(channelName, cursor, limit)` |
| 多端同步 | 同 `userId` 多 `clientId` 策略：全推 / 单端 / 排除发送端 |

### 10.3 P1 — 管理与可观测

| 能力 | 描述 |
|------|------|
| 健康检查 | `/health`（独立模式）或 `getStats()` |
| 运行指标 | 连接数、频道数、推送成功/失败、鉴权失败 |
| 管理指令 | 踢人、解散频道、广播系统公告（需管理鉴权） |
| 结构化日志 | 替换裸 `console`，对接宿主 Logger |

### 10.4 P2 — 多通道通知（Outbox）

在实时 WS 之外，提供统一通知抽象，便于业务一次投递、多通道执行：

| 通道 | 说明 |
|------|------|
| WebSocket | 已有实时通道 |
| Webhook | 回调业务 URL |
| Email | Provider 插件 |
| SMS | Provider 插件 |
| Mobile Push | FCM/APNs Provider 插件 |

**统一消息模型（建议）**

```ts
interface NotifyMessage {
  messageId: string
  msgType: "all" | "channel" | "single"
  channelName?: string
  userId?: string | string[]
  notifyType: string
  title?: string
  body: string | Record<string, unknown>
  channels: Array<"ws" | "webhook" | "email" | "sms" | "push">
  priority?: "low" | "normal" | "high"
  expireAt?: number
  meta?: Record<string, unknown>
}
```

### 10.5 P2 — 集群与高可用

- 连接层可多实例；会话路由或粘性连接
- 跨节点 Pub/Sub 扇出
- 可选 sticky + Redis adapter 文档

## 11. 协议增强草案（对客户端）

### 11.1 通用请求

```json
{
  "type": "request",
  "method": "joinChannel",
  "requestId": "uuid",
  "clientId": "uuid",
  "userId": "u1",
  "sendTime": 1710000000000,
  "data": { "channelName": "room-1" }
}
```

> 演进建议：业务参数统一放入 `data`，同时短期兼容顶层平铺字段。

### 11.2 通用成功/失败 Feedback

```json
{
  "type": "feedback",
  "requestId": "uuid",
  "res": {
    "status": true,
    "method": "joinChannel",
    "code": 0,
    "message": "ok",
    "data": {}
  }
}
```

### 11.3 建议错误码（节选）

| code | 含义 |
|------|------|
| 0 | 成功 |
| 1001 | 未登录 |
| 1002 | Token 过期 |
| 1003 | 无权限 |
| 1004 | 参数非法 |
| 1005 | 频道不存在 |
| 1006 | 限流 |
| 1007 | 消息过大 |
| 1099 | 内部错误 |

## 14. 验收标准（总览）

1. **功能**：现有 login / join / leave / logout / notify 在兼容模式下全部可用
2. **安全**：未登录无法发 notify；越权有错误码；支持 WSS 与 Origin 限制
3. **性能**：频道推送不再全表扫描；具备连接上限与限流
4. **工程**：可 npm 安装、有类型、有测试、有协议文档
5. **拓展**：至少实现 P0 清单；P1 离线与管理能力可演示
6. **独立可用**：至少一种模式（嵌入或独立）可被第二个业务系统无改核心代码接入

## 15. 风险与依赖

| 风险 | 缓解 |
|------|------|
| 协议变更导致旧客户端失败 | 兼容层 + major 版本策略 |
| 多实例一致性复杂 | 先单机强化，再引入标准 Pub/Sub adapter |
| 宿主鉴权实现质量不一 | 提供 AutProvider 参考实现与调试模式告警 |
| 多通道运营商差异 | 仅定义 Provider 接口，具体实现可外置包 |

## 16. 附录：现状能力速查

### A. 已实现

- WebSocket 服务启动（可配置端口）
- Token 登录与会话过期检查（request 路径）
- 加入/离开频道、登出
- 频道通知广播 + 最近通知缓存
- 宿主钩子：`verifyToken` / `addLog` / `addNotify`

### B. 未完成 / 不可用

- `getChannelAttribute` 路由未接通
- `getAttributes` 空数据
- `MSG_TYPE` 单播/全体
- `sys` 系统消息
- notify 鉴权
- 离线、持久化、集群、多通道
- 完善文档与工程化测试

### C. 关键消息示例（现状风格）

**登录**

```json
{
  "method": "login",
  "token": "<token>",
  "clientId": "c1",
  "requestId": "r1"
}
```

**加入频道**

```json
{
  "type": "request",
  "method": "joinChannel",
  "clientId": "c1",
  "requestId": "r2",
  "channelName": "room-1"
}
```

**发送通知**

```json
{
  "type": "notify",
  "clientId": "c1",
  "userId": "u1",
  "channelName": "room-1",
  "notifyType": "progress",
  "notifyMsg": "{\"percent\":80}"
}
```
